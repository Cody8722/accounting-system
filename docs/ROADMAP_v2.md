**2b. 完整備份與還原**
- JSON 備份目前只存 `type/amount/category/date/description/expense_type` 六個欄位，還原後錢包、位置、轉帳、受限資金全部遺失，`transfer`／`restricted` 在匯入時還會因分類為空被判無效。
- 匯入判重（日期＋類型＋金額＋分類＋備註）會把「同一天買兩次同價、備註空白」的記錄當重複丟掉，還原到新帳號會弄丟真實記錄。
- 新備份格式：帶錢包、所有記錄欄位、預算、定期、欠款；還原時重新對應 ID（轉帳配對、受限資金、`linked_income_id`、`source_*`）。
- **照片（定案，2026-11-18）：納入，備份改用 zip**（JSON 加照片資料夾）。還原時照片檔搬到新帳號的 `<user_id>/<新 record_id>/`，`records.photos` 的標記一併重新對應（`photo_id` 與檔名沿用）。匯出時可勾選是否含照片（預設不含，檔案較小）；zip 要串流處理、還原要設上傳大小上限，避免單一 worker 吃光記憶體。備份格式帶版本欄位，舊的純 JSON 備份仍可匯入。
- **照片很大時（定案，2026-11-18）：不拆成多檔**（少一片整份就壞）。匯出端用串流 zip 邊寫邊傳，記憶體用量不隨照片數增加；還原端也邊讀邊處理，並設上傳大小上限（暫定 500MB～1GB，依實際照片量調整，超過要回明確訊息，nginx `client_max_body_size` 要一起調）。真的很大時由使用者分段：匯出可選日期範圍（每份都是可獨立還原的完整 zip）、可選是否含照片（資料與照片分開）。NAS 另有每日 snapshot／backup 涵蓋照片磁碟，所以應用程式內 zip 的定位是換帳號、換機器、遷移，不是唯一的災難備份。
- **匯入模式（定案，2026-11-18）：要有「合併」，也要有「整批還原」**，匯入時讓使用者選。
- **時間必須還原得對（定案）**：備份與還原要原樣保留所有時間欄位，不能用匯入當下的時間蓋掉——`records.date`（YYYY-MM-DD）、`created_at`、`updated_at`、`unlocked_at`、照片 `uploaded_at`、欠款的 `date`／還款 `payments[].date`、錢包 `created_at`、預算與定期的相關日期。做法從簡：備份直接把時間戳記原樣存下來、還原時原樣寫回，不另外設計轉換規則；日後真的需要換格式再改（備份格式有版本欄位，改得動）。要補一個測試：匯出再匯入後逐欄位比對時間。
- **合併的判重方式**：備份帶每筆記錄的原始 `_id`（`source_id`），合併時先以它判重（同一帳號備份再合併回來就是精準的）；沒有 `source_id` 的舊備份才退回「日期＋類型＋金額＋分類＋備註」，並把 `created_at` 也納入比對，避免把「同一天買兩次同價、備註空白」誤判成重複。

**2c. 需要先決定行為的**
- 編輯記錄不連動衍生記錄：觸發過自動提領的支出改錢包，提領留在舊錢包；有拆分的收入改錢包／位置／日期，受限資金留在原處。選項：連動搬移，或直接禁止改（建議禁止）。
- 欠款還款記帳沒有錢包與位置，永遠只算在「未分類」，不進銀行／現金總額；是否讓使用者選。
- 編輯支出金額不檢查現金是否足夠（新增有「現金不足提領」流程）；是否也要確認。

**2d. 其他（中低）**：還款可超額且仍標結清；還款為「先讀再寫」連點會遺失一筆；編輯欠款成員後總已付金額未重算；後端不限金額小數位；`toggle_member_pay` 是遺留死程式碼；錢包名稱可重複、數量無上限；匯入每筆各查一次資料庫。

**2e. 前端分頁 UI（#9）**：明細頁目前以日期範圍加 `limit=200` 一次抓齊，單一範圍超過 200 筆會被截斷，需要「載入更多」或翻頁。

**2f. 記帳存完整時間戳與時區、保留照片 EXIF（2026-11-21 使用者定案方向）**：現在 `records.date` 只存 `YYYY-MM-DD`，沒有幾點幾分。
- **時間（必做）**：新記錄由前端用裝置時鐘帶三個值，後端檢查合理性後原樣存：`occurred_at`（UTC 時間戳）、`tz_offset_min`（當時時區偏移，分鐘）、`date`（當時看到的本地日期，照舊）。符合向下兼容原則：不改名、不刪欄位；舊記錄沒有新欄位，讀取時以 `date`／`created_at` 補、視為 +480，不搬遷。離線記帳的時間是按下儲存那一刻，不是同步當下。後端檢查：時間戳不可比伺服器現在晚超過一天、要與 `date`（套用偏移後）對得上，不合理就退回用伺服器時間。
- **地點（定案 2026-11-22：用 GPS 抓座標，只存座標、不轉地名）**：新增 `location`（`{lat, lon, accuracy, source}`，可為 null；`source` 是 `exif` 或 `gps`）。座標來源兩種、合併成同一個欄位：照片 EXIF 有座標就用它（拍照當下的位置，比事後按儲存更準），沒有照片或照片沒座標就用按儲存時的定位。定位的做法：前端用瀏覽器 `navigator.geolocation` 在按下儲存時取一次，不阻擋儲存（背景取、逾時約 5 秒就放棄、允許用最近的快取位置）；離線也能取，因為 GPS 不靠網路。設定裡加「記帳時記錄位置」開關，**預設關閉**，打開時才向系統要定位權限；被拒絕或取不到就是 null，不影響記帳。不轉地名（需外部服務與 CSP 放寬），顯示就用座標，之後要地圖或地名再說。原本想的手寫 `place` 文字欄位不做，要的話之後可加。座標屬敏感資料：只存在使用者自己的帳號下、隨備份原樣匯出入，不做公開分享；刪帳號時與記錄一起清除。
- **照片 EXIF（保留，不再全部壓掉）**：現在前端用 canvas 重新編碼 JPEG，EXIF 全丟。改成壓縮前先讀出 EXIF（拍攝時間 `DateTimeOriginal`、相機型號；座標不在這裡存，EXIF 有座標時寫進上面的 `location`），存進 `records.photos[].exif`（物件，欄位可空，每張約數百位元組），圖檔本身仍是壓縮後、不夾帶 EXIF（避免方向標籤造成二次旋轉，也避免座標藏在可被分享出去的圖檔裡，檔案也不會變大）。讀得到拍攝時間時可預填 `occurred_at`，使用者可改；讀不到（很多手機瀏覽器選檔時已去掉 EXIF）就用現在時間。不新增套件，只解析 JPEG 的 EXIF 區段。
- **之後再說**：時區名稱 `tz`（`Asia/Tokyo`）、座標轉地名或地圖顯示、手寫地點 `place`。
- 與 2b 的關係：備份帶 `occurred_at`／`tz_offset_min`／`location`／`photos[].exif`，原樣寫回；合併判重可用 `occurred_at` 加金額，比只有日期精準。
- 要補的測試：新記錄 `date` 與 `occurred_at`＋偏移一致；跨午夜與時區邊界日期不位移；舊記錄無新欄位時排序與統計不變；EXIF 解析（有／無／損壞檔都不得讓上傳失敗）。

**2g. 測試把關補強（2026-11-22，外部審查加獨立子代理審查，都讀程式碼確認）**：目前測試「綠燈但沒驗東西」，要先補，否則 2a、2c 的修正沒有可靠的回歸網。
- 放水的斷言：`assert status_code in [..., 500]`（伺服器回 500 也算過）在 `test_accounting.py` 25 處、`test_api.py` 33 處、`test_auth.py` 19 處；統計測試 `total_income == 0 or isinstance(...)` 幾乎必然成立；趨勢測試只檢查結構不檢查數字。逐步改成精確狀態碼與數值斷言。

- 覆蓋率門檻只涵蓋 `main.py`（75）與 `auth.py`（80），`routes/` 沒有。補上門檻。
- 並發類測試（解鎖連點、`client_id` 重送）循序呼叫重現不了競態（第二次會看到已解鎖而被擋，修前修後都過）；要用多執行緒加真 Mongo，修之前必須失敗。
- 不變量測試：同一帳號下，位置餘額（銀行＋現金）、錢包餘額、概覽 `cash_balance` 三者要一致；匯出再匯入（2b）後餘額與時間欄位不變。

**2h. 審查新發現（修之前一律先補會失敗的測試）**
- **現在就影響數字、優先修（第一個修正 PR）**：
  - 趨勢 `/accounting/trends` 先升冪排序再 `$limit`，取到最舊的 N 個月而不是最近的（`stats.py:252-253`）。
  - 環比 `/accounting/comparison` 的「本期」不含今天（`cur_end = now` 加 `$lt`，`stats.py:364,374`），且不受錢包與分類篩選影響。
  - 全域錯誤處理器 `@app.errorhandler(Exception)` 把所有 HTTP 例外都變成 500，400（壞 JSON）、413、429（限速）都被吃掉（`main.py:93-96`）。
  - 金額驗證不一致：欠款（建立／更新／還款／成員還款）、預算、定期收支各自只做 `float()` 加 `<= 0`，接受 NaN、無限大；`validate_amount` 本身接受布林（`float(True)` 為 1.0）。統一走 `validate_amount` 並加 `math.isfinite`、拒絕 `bool`。
- **併入 2a**：解鎖競態根因是 `update_one` 條件沒帶 `type: "restricted", unlocked_at: None`，改 `find_one_and_update`；定期收支套用不冪等（連按兩次產生兩筆）且不清統計快取；欠款還款的日期未驗證。
- **併入 2c**：直接刪自動提領轉帳會留下指向不存在記錄的 `source_transfer_id` 且現金變負；刪除還款產生的記帳記錄不退回欠款 `paid_amount`；解鎖後的收入改金額，配對的支出不同步；收入改支出時位置沿用收入選的而非由系統判斷；轉帳與解鎖端點沒有 `client_id` 冪等，離線佇列不能安全使用；全額受限（`amount = 0`）不寫主記錄也就沒有 `client_id`，重送會重複建立受限資金；離線重送競態時，自動提領轉帳已先寫入，主記錄撞唯一索引後轉帳留成孤兒。
- **併入 2b**：匯入接受 `transfer`／`restricted` 類型，手工檔案帶非空分類就能寫入沒有 `from_location`／`to_location`／`location` 的轉帳，要在匯入端擋掉。
- **待驗證**：借出的錢可能讓淨資產永久多算（`net_balance = cash_balance + receivable - payable`，`stats.py:199`；建立借出欠款時不產生支出，對方還款卻產生收入），影響要看欠款建立的實作；概覽 `cash_balance`（全部收入減支出）與位置餘額定義不同，只在所有記錄都有位置時才一致；垃圾桶清除不含 `invites`（要確認是否以 user 關聯）。
- **低優先**：錢包 `icon` 未跳脫就放進 HTML class 屬性（`wallet.js`、`lock.js`），只是自我 XSS，伺服器端對 `icon`、`color` 做白名單即可；`GET /records` 日期或類型參數無效時被靜默忽略。

### 階段 2.5：帳號垃圾桶與遷移代碼（排在 2b 之後）
構想：刪除帳號不是立刻刪光，先進垃圾桶並可選保留時間；給一組代碼，可把這個帳號的資料遷移到另一個帳號。遷移 = 伺服器端用 2b 的還原邏輯匯入目標帳號，所以必須在完整備份還原之後。目前沒有「刪除帳號」功能，這是新功能。

**已定案**
- 標記打在 `users` 文件上（`deleted_at`、`migrated_to`、`migrated_at` 等），來源資料不清除；資料本來就靠 `user_id` 隔離，不用在每筆資料加標記。
- 遷移到目標帳號先只做「**合併**」（來源資料加進目標、目標原有資料保留）；「取代」之後視需求再加。
- 垃圾桶期間 Email 是「軟占用」：原主人可登入還原；**有人用同一 Email 重新註冊時，註冊成功並接管該 Email**，被接管的垃圾桶帳號資料不動、保留期照舊，但失去 Email（原 Email 另存 `original_email`），之後只能靠遷移代碼搬走資料。
- 遷移走伺服器端，照片可直接複製，不受 JSON 備份大小限制。
- 安全：代碼夠長夠隨機、資料庫只存雜湊、只顯示一次、兌換限速、保留期滿失效、可撤銷；刪除帳號要重新輸入密碼；刪除帳號後既有 token 立即失效（擴充 `_token_still_valid`）；垃圾桶中的帳號排除在忘記密碼與登入鎖定流程之外。

**2.5a 已實作（自助刪除＋垃圾桶＋還原＋到期清除，不含遷移代碼）**：保留期 7/30/90 天（預設 30），另有「立即永久刪除」；到期清除由後端背景執行緒自動執行（啟動後 1 分鐘、之後每 6 小時；`ACCOUNT_TRASH_PURGE_INTERVAL_HOURS` 可調、0 停用），不需外部排程，手動用 `backend/manage_trash.py`；垃圾桶帳號登入回 403 `account_in_trash` 並引導走 `POST /api/auth/restore-account`；Email 接管、token 失效、忘記密碼排除皆照上方定案。見 `backend/account_trash.py`。

**待決定（2.5b 遷移代碼，依賴 2b）**：代碼是否單次有效；遷移過的來源帳號到期是否照樣清除（建議照樣）；是否提供「不刪帳號也能遷移」的入口（例如換 Email）。注意：在遷移代碼做出來之前，Email 被接管的垃圾桶帳號等同無法取回資料（只能等保留期滿清除）。

### 階段 3：APK 套殼前置整理
- 把 `onclick=` 改成 JS 綁事件，之後 CSP 才能拿掉 `'unsafe-inline'`，XSS 防護才真正變嚴。
- 匯出改走原生分享（WebView 預設不處理下載）。
- 確認 Service Worker 在 WebView 內離線快取與離線同步正常（殼載入遠端網頁，第一次連過之後離線可用）。
- Service Worker 更新機制要穩：記一筆時不強制重整、預先快取繞過瀏覽器 HTTP 快取（v1.19.x 已修，套殼前再驗一次）。

### 階段 4：APK 套殼
- **採「殼載入遠端網頁」**（如 Capacitor 設定載入 `https://ubuntu-server.tail886591.ts.net/`）：前端更新部署到 NAS 就生效，APK 不用跟著換；網頁沿用同源相對路徑，不需要寫死後端網址。
- 相機改用原生元件；網頁版相機不再投資。
- 取代下方長期目標的「React Native / Flutter」方向，改為套殼現有網頁。
- **APK 自行更新（不上 Google Play）**：只有原生部分變動才需要換 APK。GitHub Actions 在發版時建 APK 並附在 GitHub Release，手機用 Obtainium 追蹤該 Release（repo 公開，免權杖）；每次安裝仍需手動確認。簽章金鑰存放於 GitHub Secrets，不進 repo，並另行備份（遺失就只能重裝、本機未同步資料會丟）。
- 限制：需連到 Tailscale 才能首次載入；網址僅 tailnet 內可達，只適合自用／家人，不適用商店上架。
